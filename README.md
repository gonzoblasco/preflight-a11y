# preflight

**Your AI built the site. This proves it works — and tells the builder how to fix it.**

A pre-launch accessibility gate that reads your page with a screen reader,
then hands back a repair prompt your AI builder can execute.

[Quickstart](#quickstart) · [Why](#why-this-exists) · [What makes it different](#the-three-layers) · [How it works](#how-it-works)

</div>

---

## The problem, in one scan

Here is a real page, generated by an AI builder, scanned by Preflight. This is
what a blind visitor hears:

```
  1  document
  2  image                        ← an image with no name
  3  link, Pricing
  4  button                       ← a button with no name
  5  heading, Ship your landing page in minutes, level 1
  6  image                        ← another one
```

Everything on that page is technically valid HTML. Every attribute a linter
checks is either present or reported by axe. And a person using a screen reader
**cannot tell what those two images are or what that button does.**

No attribute-based tool shows you this. Preflight does, because it reads the page
the way it will actually be consumed.

## Quickstart

```bash
git clone https://github.com/gonzoblasco/preflight-a11y
cd preflight-a11y
npm install
npx playwright install chromium       # or use your system Chrome
npm run dev                           # http://localhost:4317
```

Then scan your own dev server (localhost is accepted — it scans *your* code, which
is the whole point):

```bash
npm run dev                     # your app on :3000
node scripts/cli.js http://localhost:3000
```

or any public URL:

```bash
node scripts/cli.js https://your-site.com --min-score 90 --fail-on-blocking
node scripts/cli.js https://your-site.com --markdown --out report.md
node scripts/cli.js https://your-site.com --json
```

> **Note:** `npx preflight-a11y …` will land **once the package is published**.
> Until then, the commands above work from a clone. There is no public npm package
> yet — this is the local-first, open-source stage.

### Scan what you are building, not what you shipped

The CLI accepts `localhost` and private addresses **by default**, because the
person running it and the machine being scanned are the same. Blocking your own
dev server protects nobody.

```bash
npm run dev                              # your app on :3000
node scripts/cli.js http://localhost:3000  # scan it while you work
```

That is the difference between a gate you run once at launch and one you run on
every change. The guard exists for the hosted server, where a stranger's URL must
never reach our network — so the remote MCP and the API refuse private hosts, and
the CLI does not. Pass `--public-only` if you want the strict behaviour locally.

Exit codes are the point: `0` pass, `1` gate failed, `2` scan error. Drop it in CI (`action.yml`) and a pull request that ships an unusable
button stops being merged.

git clone https://github.com/gonzoblasco/preflight-a11y

## Why this exists

Anyone can **detect** an accessibility bug. `axe-core` is free, Lighthouse ships
in Chrome, and every framework has a plugin. What none of them do is close the
loop:

```
detect ──► explain to a non-developer ──► hand back an instruction the builder can execute
```

AI-built sites made that gap urgent. Someone with no accessibility training can
ship a landing page in twenty minutes, and the tool that generated it will happily
produce `<button><svg/></button>` with no accessible name. That person will not
read a WCAG success criterion. They will paste a prompt.

So there are three layers, in order of importance.

---

## The three layers

### 1. The transcript

The page is walked with a screen reader and every phrase it speaks is recorded, in
order. Gaps — a role announced with no name — are marked and explained in plain
language:

```
 !  4  button  ← a button with no name — the user cannot tell what pressing it does
```

This is the observation no attribute linter can produce. It is the experience.

### 2. The verdict

One score that **refuses to be green while someone is blocked**. A page with 92
findings fixed and one unusable checkout does not get an A. `92/100 but checkout
is broken` is how a tool gets uninstalled.

### 3. The fix prompt

An ordered prompt, ready to paste into the tool that generated the page. Every
step names the element, the change, and **the announcement the reader must produce
afterwards**:

```markdown
## Step 2 — Elements must meet minimum color contrast ratio thresholds
Where: the section #pricing
Affects 2 elements that share this cause. Fix the shared source, not each element:
  - .hero > p
  - footer span
Do: Change the text or background colour. Measured: ratio 1.89:1 (needs 4.5:1),
    foreground #b9bcc4, background #ffffff.
Reader must announce: Re-run Preflight: the contrast rule reports no failing elements.
```

That last line is the difference between a suggestion and a contract. The builder
can verify its own work instead of guessing "looks good to me".

**Measured, not asserted:** three model families were given this prompt and their
output was re-scanned by the same engine. 95.8% of findings closed, zero
regressions, and both editors preserved every image, link and word on the page.
A live product was repaired from **49/100 F to 100/100 A** this way, with every
step verified by re-scanning the deployed URL.

## What it does not do

This section is not fine print. A tool that overclaims is trusted once.

- **It does not certify anything.** Automated checks catch roughly a third of
  accessibility defects. Every report says so, in the report body.
- **The transcript is virtual.** It reflects what the DOM declares, not how
  VoiceOver or NVDA times a specific announcement in a specific browser.
- **It does not crawl.** One URL per scan, by design.
- **It does not fix your code.** It measures, explains, and hands you the
  instruction. Editing your project is your builder's job — and keeping that
  boundary is why the MCP server can be called without an approval prompt.
- **A green score is not compliance.** It means no *detectable, blocking* defect
  was found on that page at that moment.

## How it works

```
URL ──► real browser ──► axe-core (60+ rules) ──► screen reader ──► score
                                                         │
                                                         ▼
                                                  fix prompt
```

- **Real browser, not a parser.** Animations are frozen and visual state is
  sampled until stable before analysis — a page measured mid-fade reports contrast
  failures that no user ever sees.
- **Deterministic.** The same page produces the same findings on every run;
  otherwise a score is not evidence.
- **SSRF-guarded.** Private addresses are refused on the literal host *and* after
  DNS resolution. A scanner that takes arbitrary URLs is otherwise a free port
  scanner.

### Surfaces

One engine, several delivery surfaces — the engine imports no UI or server
framework:

| Surface | For |
|---|---|
| **CLI** `node scripts/cli.js` | developers, CI |
| **GitHub Action** | block a PR that ships a blocking defect |
| **Web report** | a report a non-developer can read and forward |
| **MCP server** (stdio or HTTP) | the gate inside an AI builder's loop |

The MCP tools are **read-only by design** (`scan_url`, `read_announcements`,
`assert_announcement`, `get_fix_prompt`, `explain_rule`). Read-only tools run
without an approval prompt in hosted builders, which is what makes the
integration usable instead of annoying.
